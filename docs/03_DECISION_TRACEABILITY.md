# 03｜决策追踪、版本覆盖与未决事项

## 来源和作用

| 版本 | 产物定位 | 使用规则 |
| --- | --- | --- |
| V1.1 | 产品/架构/工作流总规范与首轮审查 | **产品范围和明确已确认事项** 的基础来源 |
| V1.2 | P0 可行性核实与技术风险 | 限制实现宣称的保证等级，不覆盖用户已确认的目标 |
| V1.3 | 实验、测试证据、F1/F2 门禁 | 作为 E00–E07 的验收与冻结依据 |
| V1.4 | LMP V1、SDK、ACK、恢复契约候选 | 为 **最新协议字段/语义优先来源**，但仍非 F2 正式冻结 |

## 已确认事项必须继承

- 新的独立本机 Windows 项目；Web 控制台与独立 Git 仓库。
- 首版模块分发选 B：内置模块和本地开发者模块。
- 人工接管后不自动恢复写入，必须在核对后由用户明确确认。
- 网页 AI 可请求受控的本地只读文件查询；CMD/PowerShell 与测试能力进入首版 P0。
- Core 不把 Agent 自报或协议 ACK 直接视为业务验收通过。

## 跨版本采用优先级（建议）

1. 新的**用户明确决策**优于此前没有冻结的建议；产生不兼容影响时记录 ADR。
2. 产品需求优先查 V1.1；技术限制优先查 V1.2。
3. 实验执行与准入门槛优先查 V1.3；V1.4 E00 对最小模拟验证有更具体的测试合同。
4. LMP/SDK、任务三轴、连接端点/会话身份与授权字段优先查 V1.4；不要从 V1.1 老草案复制过时的字段名。
5. 对于未覆盖的事项，标注 OPEN，不得推断已冻结。

## 尚需决议的工程问题（OPEN）

| 事项 | 冻结前的要求 |
| --- | --- |
| F1 正式批准 | 用户逐条审阅不变量，并记录 APPROVED / NEEDS CHANGE |
| LMP Wire Schema | E00 验证身份、消息信封、反序列化和版本协商 |
| SDK V1 | E00 验证模块生命周期、能力、超时与进程恢复 |
| ChatGPT / 网页 Bridge | E02 验证实际支持路径、会话身份和准确交付 |
| WorkBuddy GUI | E03 按真实证据确定 G0–G3 能力等级 |
| DSH ACP | E04 验证目标安装版本支持的实际协议功能 |
| CMD/Test Runner | E05 证明审批和副作用检查；强隔离需另行验收 |
| 工作流恢复 | E06 验证未知结果不得盲目重试 |

## 文档维护建议

未来新版本使用新的 `versions/vX.Y/` 目录，保留历史而不原地覆盖。请在顶层 README 和本文件中更新“最新推荐入口”“候选/冻结状态”和新 ADR 链接。只有实际测试完成、证据齐全且通过评审后，才能把相应项改为 FROZEN。
