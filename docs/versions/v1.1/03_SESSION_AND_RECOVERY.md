# 03｜会话控制权、人工接管与恢复规范 V1.1

**状态：用户策略 CONFIRMED；字段/状态机 REVIEW DRAFT**

## 1. 已确定策略
- B：用户可在自动化期间人工介入；检测到与自动化一致性冲突后，停止新写入并对账。
- A：人工接管结束后，即便系统核对通过，也必须用户主动确认才能恢复自动写入。
- 用户的优先权是 Hub 内部调度规则，并不表示 Windows 禁止用户直接操作应用。

## 2. 身份与控制权
`sessionBindingId` 是 Hub 记录的稳定绑定 ID；`externalSessionIdentity` 是真实应用中的会话证据。网页需要核对浏览器 Profile、来源、标签页/文档、对话身份与轮次；Windows GUI 需要核对应用、进程创建证据、窗口、工作区和会话线索。单独依赖 Tab ID、PID、HWND 或窗口标题均不足。

Ownership 状态：`AVAILABLE`、`AUTOMATION_OWNED`、`TAKEOVER_PENDING`、`HUMAN_OWNED`、`RECONCILING`、`SUSPENDED`。绑定可信状态：`VERIFIED`、`PROVISIONAL`、`LOST`。这些状态与 Task 的 `RUNNING`、`FAILED` 等独立。

## 3. 写入控制
一次自动写操作必须经过有效 Binding、Core 授权、`ownershipEpoch`、有效 Lease 和资源锁核对。用户接管时 Core 阻止新的写入，递增 Epoch，使过期写许可失效；Adapter 在实际提交动作前二次检查。

无法保证所有 GUI API 调用都能被原子性撤销：旧消息已经进入目标应用时，Lease 过期并不使其停止。进入核对状态而非声称“取消成功”。

## 4. 并发
- 同一 Session：默认单个自动写入所有者，其他写任务排队。
- 不同 ACP 会话：仅在 Adapter 能力声明与资源锁允许时并行。
- GUI 全局鼠标/焦点：可能需要额外 Interaction Lock。
- 共享文件：写入采用 Resource Lock 和版本冲突检查。
- 用户接管单个会话，不无故暂停无资源冲突的其他会话。

## 5. 人工介入判断
Hub 里的“接管”按钮可明确识别人为请求；外部 GUI 变化通常只能提供变化证据，不应宣称已准确判断由哪个人操作。未知来源用户消息、会话错配、输入框异常变化等触发保守暂停与核对。窗口失焦本身不足以判定接管。

## 6. 恢复决策矩阵
- 可证明任务尚未发送：在有效授权下重新排队。
- 提交是否成功未知：`OUTCOME_UNKNOWN`，禁止直接重发。
- 已提交且仍在执行：恢复观察，不重复提交。
- 已结束但结果尚未持久化：核对会话与轮次后补采集。
- 结果已持久化但尚未交付：确认目的会话及交付许可后幂等补交付。
- 绑定对象变更或用户人工接管：冻结原自动写入；对账并等待明确恢复确认。
- 证据冲突或不足：人工复核或终止剩余流程。

## 7. 不变量
S-01 单 Session 同时最多一名自动写所有者。
S-02 人工接管阻止新写入。
S-03 旧 Epoch/Generation 不可用于新写入。
S-04 Lease 过期不证明外部动作停止。
S-05 只允许将结果关联到可证明的 Task/Turn。
S-06 GUI 推断不等于外部业务验证。
S-07 Core 重启、Adapter 重连不自动恢复人工接管前的写入。
S-08 人工恢复必须由用户明确确认，并记录审计事件。
